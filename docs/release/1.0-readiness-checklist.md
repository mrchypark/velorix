# Velorix 1.0 Release Readiness Checklist

Status: **not ready**.

Velorix 1.0 is blocked until every row in
`docs/architecture/production-readiness-status.md` is present and has status
`complete` with `Blocking Tasks` set to `none`. Any `partial` row, `missing`
row, uncleared blocking task, absent required row, missing verification command,
or missing evidence artifact keeps the release blocked.

## Local First E2E Profile

The local first E2E profile is intentionally weaker than the 1.0 release gate.
It exists so the project can run a complete local functional pass while
deployed topology and live evidence remain follow-up hardening work.

Run the full local first E2E profile with deployed product evidence enabled:

```bash
VELORIX_FIRST_E2E_RUN_PRODUCT=1 \
VELORIX_FIRST_E2E_PRODUCT_PROFILE=required \
scripts/run-first-e2e-readiness.sh
```

The script runs local dependency governance, RustFS S3-compatible live tests and
benchmarking, RustFS production GC evidence generation, ingest-writer image
build, vind/vCluster Kubernetes tests with that image configured, a manually
callable two-replica vind product slice, and the
`readiness-report --first-e2e-artifacts` command. A passing run ends with:

```text
production_ready=true
blocking_reasons=0
readiness_report=target/release-evidence/first-e2e-readiness-report.json
```

The RustFS portion writes the production GC artifact family together:

```text
target/release-evidence/rustfs-production-gc-seed.json
target/release-evidence/rustfs-production-gc-run.json
target/release-evidence/rustfs-production-gc.json
target/release-evidence/rustfs-production-gc-validation.json
```

The last file is produced by `rustfs-production-gc-evidence-validate`, which
binds the RustFS gate JSON, seed fixture, executed `GcRunV1`, and production GC
evidence to the same authority store, run id, fixed retain-1 policy, persisted
run digest, seed-declared full deleted object keys, and artifact paths.

When the same RustFS backend is kept alive for the product slice, the wrapper
passes the same run-local non-default RustFS credentials to both
`scripts/run-rustfs-s3-gate.sh` and `scripts/run-vind-product.sh`; it does not
fall back to RustFS default credentials.

Useful rerun shortcuts:

```bash
VELORIX_FIRST_E2E_SKIP_RUSTFS=1 \
VELORIX_FIRST_E2E_SKIP_DOCKER_BUILD=1 \
VELORIX_FIRST_E2E_SKIP_VIND=1 \
VELORIX_FIRST_E2E_PRODUCT_EVIDENCE=target/velorix-product/product-evidence.json \
  scripts/run-first-e2e-readiness.sh
```

The skip flags reuse existing artifacts at the default paths. Use them only
after a full run has already generated those artifacts. Readiness schema v5
still requires either `VELORIX_FIRST_E2E_RUN_PRODUCT=1` with
`VELORIX_FIRST_E2E_PRODUCT_PROFILE=logical-fencing` or `required`, or an existing
`VELORIX_FIRST_E2E_PRODUCT_EVIDENCE` artifact with non-dev standing-runtime
fencing, at least two API replicas, metadata adversarial smoke, passing
multi-replica fencing smoke, and the referenced sibling evidence artifacts.
When `VELORIX_FIRST_E2E_SKIP_RUSTFS=1` is combined with
`VELORIX_FIRST_E2E_RUN_PRODUCT=1` against RustFS-backed production GC evidence,
the wrapper requires explicit matching S3 credentials for the reused backend.
Provide either `VELORIX_FIRST_E2E_PRODUCT_AWS_ACCESS_KEY_ID` and
`VELORIX_FIRST_E2E_PRODUCT_AWS_SECRET_ACCESS_KEY`, or `AWS_ACCESS_KEY_ID` and
`AWS_SECRET_ACCESS_KEY`, or `VELORIX_RUSTFS_ACCESS_KEY` and
`VELORIX_RUSTFS_SECRET_KEY`.
When `VELORIX_FIRST_E2E_RUN_PRODUCT=1` is used without an explicit
`VELORIX_FIRST_E2E_INGEST_WRITER_LIFECYCLE_EVIDENCE`, the wrapper consumes the
product slice's freshly generated
`target/velorix-product/ingest-writer-lifecycle-attestation.json`; explicit
overrides and no-product reruns use the supplied standalone lifecycle
attestation path. The default first E2E release benchmark comparison uses
`VELORIX_FIRST_E2E_MAX_REGRESSION_FRACTION=0.35`; set a lower value when you
want a stricter local performance gate.

For this profile, dependency governance is satisfied by:

```bash
mkdir -p target/dependency-governance
cargo deny -f json check -W unmaintained \
  2> target/dependency-governance/cargo-deny.jsonl
cargo run -p velorix-cli -- dependency-governance-validate \
  --manifest dependency-governance.json \
  --cargo-deny-json target/dependency-governance/cargo-deny.jsonl \
  --json > target/dependency-governance/local-dependency-governance-evidence.json
```

The local first E2E readiness report uses:

```bash
cargo run -p velorix-cli -- readiness-report \
  --evidence <evidence-json> \
  --first-e2e-artifacts \
  --dependency-governance-evidence target/dependency-governance/local-dependency-governance-evidence.json \
  --s3-release-benchmark-gate-evidence target/release-evidence/s3-release-benchmark-gate.json \
  --production-gc-run-evidence target/release-evidence/rustfs-production-gc.json \
  --rustfs-production-gc-validation-evidence target/release-evidence/rustfs-production-gc-validation.json \
  --ingest-writer-lifecycle-evidence <ingest-writer-lifecycle-json> \
  --standing-runtime-product-evidence target/velorix-product/product-evidence.json \
  --json
```

Under `--first-e2e-artifacts`, the readiness report still requires production
GC evidence, RustFS production GC family validation evidence, S3-compatible
benchmark evidence, ingest-writer lifecycle attestation, a deployed product
evidence artifact for standing-runtime fencing, and dependency
governance validation. Broad Feldera-backed runtime execution is not proven by
this profile. The current DBSP adapter remains a local spike; the next Feldera gate
is the package-first `StandingProgramRuntime` compatibility proof described in
`docs/superpowers/specs/2026-05-27-feldera-package-first-runtime-design.md`.

This profile requires an ingest-writer lifecycle attestation before it can
generate a passing readiness report. For a full product run, the default source
is `target/velorix-product/ingest-writer-lifecycle-attestation.json`; for a
reuse-only run, provide `VELORIX_FIRST_E2E_INGEST_WRITER_LIFECYCLE_EVIDENCE` or
keep the standalone default
`target/velorix-k8s/ingest-writer-lifecycle-attestation.json`. That attestation
must prove Pod-internal ingest-writer append completion, multi-pod overlap
rejection, adjacent append, crash/restart reconstruction, leader handoff, and
no-PVC operation for the same deployment and authority store as the production
GC evidence. It must also include Job/Pod UID and container image ID provenance
for each lifecycle probe, plus sibling job-log artifacts referenced by
`evidence_files`, so boolean pass fields remain tied to the concrete deployed
Kubernetes work. Its `attested_at`
timestamp must be RFC3339, no more than 15 minutes in the future, and no older
than 24 hours when `readiness-report` validates it. Official CI/nightly S3
artifact upload and any remaining `partial` status-matrix rows remain 1.0
release blockers until the matrix reaches `complete`.

For a manually runnable product slice, use `scripts/run-vind-product.sh`. That
path deploys RustFS plus `velorix-api` to vind/vCluster and exposes REST
endpoints for health, relation registration, ingest, and standing-runtime view
query.
When `VELORIX_FIRST_E2E_PRODUCT_EVIDENCE` points at that script's
`product-evidence.json`, `scripts/run-first-e2e-readiness.sh` additionally
validates the product REST evidence, verifies generic `/v1/query` remains absent
from OpenAPI, and requires the metadata standing-runtime adversarial smoke plus a
passing two-replica fencing smoke and local API-pod failover smoke. Product
evidence from the default
`unsafe-dev-only` profile is useful for REST smoke, but it cannot satisfy
readiness schema v5.
Set `VELORIX_FIRST_E2E_RUN_PRODUCT=1` to have the first-E2E script run
`scripts/run-vind-product.sh` itself and then consume
`target/velorix-product/product-evidence.json`. Use
`VELORIX_FIRST_E2E_PRODUCT_PROFILE=logical-fencing` when the first-E2E run must
exercise the explicit Hiqlite logical-fencing product slice; that profile runs
two API replicas with `VELORIX_STANDING_RUNTIME_FENCING=logical-fencing`,
`VELORIX_META_BACKEND=hiqlite`, and requires `VELORIX_HIQLITE_NODES` plus
`VELORIX_HIQLITE_API_SECRET` to be set before deployment. It leaves
`VELORIX_STANDING_RUNTIME_FAILOVER_SMOKE=auto`, so the product evidence must
include sibling `standing-runtime-failover-smoke.json` with
`standing_runtime_fencing.local_api_pod_failover_smoke.status=pass`. The local
first-E2E wrapper also accepts `VELORIX_FIRST_E2E_PRODUCT_PROFILE=required`
when the product slice uses Hiqlite required fencing with backend-authoritative
time evidence. That profile passes `VELORIX_REQUIRE_HIQLITE_BACKEND_TIME=1`,
requires two API replicas, and fails closed unless the product evidence reports
`backend_time_source_kind=raft_replicated_authority_time`,
`production_multi_writer_safe=true`, and `production_bounded_failover_safe=true`.
When the first-E2E product run reuses a real external S3-compatible authority,
set `VELORIX_FIRST_E2E_PRODUCT_OBJECT_STORE_DURABILITY_ATTESTATION_FILE` to a
matching `object-store-durability-attestation.json` generated by
`scripts/attest-object-store-durability-policy.sh`; the wrapper forwards it to
`scripts/run-vind-product.sh`. The wrapper rejects that variable for its
internally generated RustFS authority because that path is local development
evidence and cannot clear product-complete durability policy.
For the public ingress/TLS/auth gate, either provide
`VELORIX_FIRST_E2E_PRODUCT_INGRESS_TLS_AUTH_ATTESTATION_FILE` with a matching
`ingress-tls-auth-attestation.json`, or set
`VELORIX_FIRST_E2E_PRODUCT_INGRESS_ENDPOINT_URL` and
`VELORIX_FIRST_E2E_PRODUCT_INGRESS_CONTROLLER` so `scripts/run-vind-product.sh`
can invoke `scripts/attest-ingress-tls-auth.sh` against the externally reachable
HTTPS endpoint. Set `VELORIX_FIRST_E2E_PRODUCT_EVIDENCE_LEVEL=product-complete`
when the first-E2E product slice is expected to fail closed unless every
product-complete gate is present.

## Product Serving Scope

Velorix 1.0 also includes the API serving scope described in
`docs/architecture/api-serving-scope-v1.md`. The release target is not only a
durable storage/query substrate: it must support governed data endpoints that
bind stable routes or tool names to persisted queries, production table scans,
or trusted standing-view artifacts after the relevant artifact trust gates pass.
Those endpoints must have request
parameter validation, response-shape contracts, OpenAPI-compatible catalog
metadata, query/cost policy linkage, and immediate-response paths from trusted
standing-runtime materialized state where available.

This scope is cross-cutting and does not add another required status row. It is
validated through the existing `DataFusion policy`, `table registry`, `Feldera
artifact registry`, `benchmark gate`, `S3-compatible tests`, and `Kubernetes
operator` rows.

  the release remains blocked until `scripts/run-rustfs-s3-gate.sh` or an

  `gc-production-evidence` verifies that live backend, and the resulting

## Fail-Closed Rule

Do not mark 1.0 ready unless all of these checks are true:

- `docs/architecture/production-readiness-status.md` has no `partial` status.
- `docs/architecture/production-readiness-status.md` has no `missing` status.
- Every required row's `Blocking Tasks` cell is `none`.
- Every required status row listed above is present.
- Every verification command above passed on the same candidate commit.
- Every evidence artifact above is recorded and reviewable.
- The release workflow was dispatched with a reviewable readiness evidence
  artifact path, and that file exists in the workflow workspace.
- The release workflow was dispatched with reviewable production GC, RustFS
  production GC validation, ingest-writer lifecycle, and standing-runtime
  product evidence paths; all files exist in the workflow workspace.
- If the release workflow was dispatched with any Feldera artifact input, it
  was dispatched with reviewable Feldera spec, metadata, and artifact package
  paths; all files exist in the workflow workspace and the workflow uploaded
  the generated Feldera hash evidence. This optional diagnostic is not a
  product-completion blocker when omitted.
- The artifact-gated `readiness-report` command in the required gates table
  returned `production_ready=true` with every required release artifact path.

Required status check:

```bash
cargo run -p velorix-cli -- release-status-validate \
  --status-matrix docs/architecture/production-readiness-status.md
```

This command must exit zero before 1.0 can be considered ready. It fails on
missing required rows, duplicate rows, any status other than `complete`, or any
required row whose `Blocking Tasks` cell is not `none`.
