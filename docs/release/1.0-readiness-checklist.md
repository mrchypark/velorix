# Velorix 1.0 Release Readiness Checklist

Status: **not ready**.

Velorix 1.0 is blocked until every row in
`docs/architecture/production-readiness-status.md` is present and has status
`complete` with `Blocking Tasks` set to `none`. Any `partial` row, `missing`
row, uncleared blocking task, absent required row, missing verification command,
or missing evidence artifact keeps the release blocked.

## Required Status Rows

The architecture status matrix must contain exactly these 1.0 contracts:

- ingest
- relation catalog
- object-store capability
- ownership
- checkpoint lifecycle
- state substrate
- DataFusion policy
- table registry
- Feldera artifact registry
- benchmark gate
- S3-compatible tests
- Kubernetes operator
- GC
- dependency governance

Current status source:
`docs/architecture/production-readiness-status.md`.

Current release decision: blocked, because the status matrix still contains
`partial` rows.

## Product Serving Scope

Velorix 1.0 also includes the API serving scope described in
`docs/architecture/api-serving-scope-v1.md`. The release target is not only a
durable storage/query substrate: it must support governed data endpoints that
bind stable routes or tool names to persisted queries, production table scans,
recovered materialized views, or trusted standing-view artifacts after the
relevant release-provenance gates pass. Those endpoints must have request
parameter validation, response-shape contracts, OpenAPI-compatible catalog
metadata, query/cost policy linkage, and immediate-response paths from
materialized or checkpoint-recovered state where available.

This scope is cross-cutting and does not add another required status row. It is
validated through the existing `DataFusion policy`, `table registry`, `Feldera
artifact registry`, `benchmark gate`, `S3-compatible tests`, and `Kubernetes
operator` rows.

## Known Blocked Gates

These are required before 1.0, but this repository does not yet expose an
executable release command for them:

- GC production live evidence: the production evidence generator exists, but
  the release remains blocked until a production GC run has already persisted
  live `GcRunV1` and checkpoint-retention records on the RustFS/S3-compatible
  authority, `gc-production-evidence` verifies that live backend, and the
  resulting artifact is attached to the readiness report.

## Fail-Closed Rule

Do not mark 1.0 ready unless all of these checks are true:

- `docs/architecture/production-readiness-status.md` has no `partial` status.
- `docs/architecture/production-readiness-status.md` has no `missing` status.
- Every required row's `Blocking Tasks` cell is `none`.
- Every required status row listed above is present.
- Every verification command above passed on the same candidate commit.
- Every evidence artifact above is recorded and reviewable.
- The release workflow was dispatched with a reviewable readiness evidence
  artifact path, and that file exists in the workflow workspace.
- The release workflow was dispatched with reviewable Feldera spec, metadata,
  artifact package, and release provenance paths; all files exist in the
  workflow workspace and the workflow uploaded the generated Feldera evidence.
- The artifact-gated `readiness-report` command in the required gates table
  returned `production_ready=true` with every required release artifact path.

Required status check:

```bash
cargo run -p velorix-cli -- release-status-validate \
  --status-matrix docs/architecture/production-readiness-status.md
```

This command must exit zero before 1.0 can be considered ready. It fails on
missing required rows, duplicate rows, any status other than `complete`, or any
required row whose `Blocking Tasks` cell is not `none`.
